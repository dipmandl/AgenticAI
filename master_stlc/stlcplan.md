# Generic Claude STLC Project

## Master Architecture & Implementation Plan

---

# 1. IMPORTANT — IMPLEMENTATION INSTRUCTION

This document is the **source of truth** for building the Generic Claude STLC Project.

The objective is to create a reusable, project-agnostic Claude project that can be integrated into different software repositories and execute the complete Software Testing Life Cycle (STLC).

Claude must NOT treat this document as a simple task list or execute the STLC pipeline immediately.

Claude must use this document to **design and build the reusable Claude project itself**.

Before implementation:

1. Read and understand the complete plan.
2. Analyze the current repository/project structure.
3. Determine the Claude environment capabilities and conventions available.
4. Identify all required:

   * Agents
   * Skills
   * Hooks
   * Commands
   * Configuration
   * Templates
   * Artifact/state management
   * Orchestration
5. Map every requirement in this document to one or more project components.
6. Identify contradictions, missing implementation details, or technically impossible requirements.
7. Do not silently remove or weaken requirements from this plan.
8. If an implementation detail is not explicitly defined, choose the most generic, maintainable, and extensible implementation.
9. Do not introduce project-specific assumptions into the reusable core architecture.
10. Keep framework-specific behavior inside framework-specific skills rather than the core orchestrator.
11. Keep project-specific configuration separate from reusable STLC logic.
12. Do not modify existing application code, existing tests, or existing automation merely to demonstrate the framework.

## Implementation Priority

Follow this priority order:

1. Requirements in this master plan
2. Safety and permission rules
3. Generic/reusable architecture
4. Existing repository conventions
5. Framework-specific conventions
6. Implementation convenience

---

# 2. OBJECTIVE

Build a complete, reusable Claude project capable of executing an end-to-end STLC pipeline for arbitrary software projects.

The project should support the lifecycle:

```text

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
```

The system must work independently with different repositories without requiring the core architecture to be rewritten for every project.

# 3. CORE ARCHITECTURAL PRINCIPLES

## 3.1 Generic by Default

Do not assume:

* Programming language
* Application framework
* Test framework
* Automation framework
* Repository structure
* UI technology
* API technology
* CI/CD provider
* Package manager
* Database
* Cloud provider

The system must inspect the repository and determine what exists.

---

## 3.2 Existing Code Protection

Existing:

* Application code
* Test cases
* Automation
* Configuration
* Dependencies
* CI/CD configuration

must not be modified automatically unless permission has been provided.

The system may freely analyze existing code.

New files generated by the current pipeline may be created and reviewed according to the configured permissions.

---

## 3.3 Never Decide From Story Title Alone

When a user provides a story or requirement:

* Read the complete content.
* Extract acceptance criteria.
* Analyze the repository.
* Search for the related implementation.
* Search existing tests.
* Search existing automation.
* Identify impacted areas.
* Compare expected functionality with actual implementation.

Never conclude that functionality exists or does not exist based only on a title.

---

## 3.4 Idempotency

Running the same pipeline multiple times must not blindly create duplicate:

* Test plans
* Test cases
* Feature files
* Automation tests
* Tags
* Reports

The system must detect existing artifacts and reuse them where appropriate.

---

## 3.5 Traceability

Maintain traceability throughout the entire pipeline:

```text

  ↓

  ↓

  ↓
Test Plan
  ↓
Test Case
  ↓
Gherkin Scenario
  ↓
Automation Test
  ↓
Execution
  ↓

  ↓
Self-Healing / Defect
```

Every generated test should have a stable identifier.

# 4. CLAUDE PROJECT ARCHITECTURE

The resulting Claude project must separate responsibilities into:

```text
Agents
Skills
Hooks
Commands
Configuration
Templates
Artifacts
State
Orchestrator
```

## Agents

Agents perform reasoning and specialized STLC responsibilities.

## Skills

Skills contain reusable domain and framework knowledge.

## Hooks

Hooks perform deterministic validation, lifecycle processing, safety checks, and metrics collection.

## Commands

Commands provide user-friendly entry points into the STLC workflow.

## Configuration

Configuration controls:

* Models
* Frameworks
* Permissions
* Execution behavior
* Retry limits
* Reporting
* Project-specific settings

## Templates

Templates standardize generated artifacts.

## Artifacts

Artifacts are persistent outputs passed between STLC phases.

## State

State records pipeline progress and allows resuming interrupted workflows.

## Orchestrator

The orchestrator controls the complete lifecycle but must not contain framework-specific implementation logic.

# 25. SELF-HEALING SAFETY

The system must never make a failing test pass by weakening the test.

For example, it must not:

* Remove an assertion simply because it fails.
* Change expected business behavior without evidence.
* Skip a test just to make the suite green.
* Remove validation from a test.
* Change acceptance criteria.

Self-healing should correct automation implementation problems, not hide product defects.

---

# 26. RERUN STRATEGY

After self-healing:

1. Rerun affected failed tests.
2. Compare previous and new results.
3. If they pass, mark them as healed.
4. If they fail again, reclassify the failure.
5. Stop after the configured retry/self-healing limit.

Default values should be configurable.

Example:

```yaml
max_self_healing_iterations: 2
max_rerun_attempts: 2
```

Never create infinite retry loops.

```text
        ↓

        ↓
```
